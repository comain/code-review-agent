# 修复会话工作流

## 目标

在不扩大改动范围的前提下，针对报告中选中的问题完成受控修复，并通过二次复核后提交 MR。

## 执行规则

1. 先确认问题范围和修复边界，再确认修复方案，最后才开始改代码。
2. 修复范围只覆盖用户明确选中的问题，以及完成这些修复所必需的最小联动代码。
3. 不允许把“顺手优化”“顺手重构”混入修复。
4. 每次改动后都要重新审视目标问题是否真正修好，是否引入新风险。
5. 如果复核不通过，优先做定点增量修改，不回退到大规模重写。
6. 提交 MR 时必须说明本轮修复覆盖了哪些问题、仍有哪些边界未处理。

## 对话阶段

### 1. 范围确认

- 和用户确认本轮到底修哪些问题
- 确认不能动的边界
- 确认是否允许补测试、补配置、补保护逻辑

### 2. 方案确认

- 按问题逐个说明修复思路
- 对可能影响行为或兼容性的改动要明确说明
- 得到用户“可以开始修复”的明确确认后再进入代码修改

### 3. 修改与复核

- 在独立工作区改代码
- 复核关注：
  - 目标问题是否修复
  - 是否越界修改
  - 是否引入新的并发、超时、重试、幂等、异常处理风险

### 4. 交付与确认

- 推送独立修复分支
- 创建指向用户原始分支的 MR
- 向用户回复修复结果和 MR 地址
- 等待用户确认通过；若用户不满意，重新从“范围确认”开始

## 输出要求

- 与用户沟通时使用中文
- 方案说明简洁、可执行
- 自检结论必须明确回答“是否通过”

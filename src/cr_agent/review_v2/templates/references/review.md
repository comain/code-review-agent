# CR v2 Review Prompt Reference

本 prompt reference 供 `cr_agent` CR v2 调用 `opencode` 时使用，目标是稳定地产出结构化静态分析结果，而不是自由格式报告。

## 输入上下文

- 本地仓库工作目录由任务服务准备好，直接在当前工程上分析
- 优先关注当前分支相对目标分支的增量变更；若缺少 diff 信息，则分析当前分支 HEAD 附近改动热点
- 若调用参数包含业务元数据、流水线信息、提交号，结合这些信息理解上下文
- 若调用参数给出“本次变更的非测试文件”，以这些文件为主审查范围

## 审查边界

- 只关注本次变更直接引入或直接暴露的问题
- 忽略测试类、测试目录、样例代码和临时验证代码
- 未变更文件只有在被本次变更直接调用、修改了使用方式、或者本次变更显著放大其风险时，才能作为问题输出
- 所有自然语言内容必须使用中文，JSON key 保持英文

## 审查标准

报告问题时优先看代码是否存在真实发布风险，而不是是否符合个人偏好。能明确证明的缺陷应输出 finding；依赖外部配置、框架语义、第三方约定或业务背景时，使用“需确认”“存在风险窗口”“建议核实”等措辞，避免把可能性写成必然故障。

每个 reviewer 都应按五个维度审查，但只输出自己 reviewer profile 范围内最有证据的问题：

1. 正确性：需求覆盖、边界值、空值、异常路径、竞态、状态不一致、重复执行。
2. 可读性与简单性：命名、控制流、模块组织、无收益抽象、死代码或兼容残留。
3. 架构与契约：模块边界、依赖方向、API/schema/callback/report 契约、迁移与回滚。
4. 安全：输入输出边界、鉴权、注入、敏感信息、外部数据和模型输出不可信。
5. 性能与稳定性：N+1、无界查询/循环、同步远程调用、批处理饥饿、超时/重试/背压。

## 必查高风险项

1. 需求覆盖与行为回归。
2. 并发、锁、线程池、异步任务、超时和重试。
3. 回调接口防重放、防重复执行、幂等键与 CAS 保护。
4. 状态机终态保护、非法状态回滚。
5. 配置上限、批处理排序、下游写接口重试语义。
6. 异常处理、资源释放、日志可观测性。
7. SQL/安全/性能问题。

## 审查流程

1. 先理解 CI/CI 请求、分支、commit、变更文件和 diff 范围。
2. 先看测试和验证信号来理解意图，但不要把“测试通过”当作充分证明。
3. 按五个维度检查实现，只输出本次变更直接引入或直接暴露的问题。
4. 对 callback、重试、幂等、状态机、配置上限、批处理、下游写、SQL、安全或性能敏感路径，最终输出前必须应用 `static-analysis-checklist.md`。
5. 对不确定结论做 false-positive 控制：说明需要确认的外部条件，而不是输出确定性故障。
6. 输出前做 first-principles check：目标是什么、实现是否是最简单正确方案、生产中如何证明、最坏影响和防护是什么。

## 输出要求

只输出任务服务要求的 JSON 对象，不补充 Markdown 解释。

## 结果规则

- `pass_check=true` 仅在不存在 `fatal/high` 级问题时使用
- `score` 以 100 为满分，按问题严重程度扣分
- `findings.file` 必须是仓库相对路径
- `findings.line` 无法确定时可省略，但应尽量给出
- `summary`、`title`、`detail`、`suggestion` 必须为中文
